Emil's skills, explained

19 checklists from a design engineer that stop an AI making small, common mistakes in animations and interfaces. You install them once. Claude then builds, reviews and tidies your UI to his standards.

The source is Emil Kowalski's repository, github.com/emilkowalski/skills (MIT licence). They are installed in this workspace's repository under .claude/skills.

The idea, in five-year-old words

An AI can build a button that slides in. It cannot always tell whether the slide feels right. The usual slip: it picks the wrong curve, so things start slow and then rush, which feels sticky. A good curve starts fast and settles gently.

Emil's skills are a list of these small slips, with the fix for each. Claude reads the list before it builds, so it doesn't make them. Press the button and watch the same slide drawn both ways.

ease-out

Same distance, same 600 ms. The grey one hangs and then lunges, which is what "ease-in" does to something entering. The blue one arrives quickly and settles, which is what the skills ask for. Slowed down here so you can see it. Real interface motion is usually under 300 ms.

Two ways to start a skill

Correction to what I said earlier. I told you to just ask in plain words for any of them. That is true for 14 of the 19. Five only run when you type their name with a slash, and plain words will not start them: /review-animations, /prototype, /pick-ui-library, /learn-taste and /ask-emil.

AUTO Just describe the job

Say "animate this drawer" or "it stutters when I scroll". Claude picks the skill whose description matches. Works for the other 14.

/SLASH Type the name

Type /review-animations in Claude Code, then say what to look at. These five are deliberately manual so they never fire unasked.

Quick start: three things to try

  1. Not sure which skill?Type /ask-emil and describe what you are doing. It names the one to use and why.
  2. Building something"Animate the quote drawer opening." The animate skill decides whether it should move at all, then the curve, length and how it can be interrupted.
  3. Checking before you shipType /review-animations on your changes. It is strict by design: it flags first and approves only when earned.

The manual: all 19

AUTO start by describing the job. /SLASH start by typing the name. READ-ONLY never edits your code.

Build

animate AUTOOne animation on the web, decided in order: should it move, why, which properties, which curve and length, how it is interrupted, how it leaves. Then it writes it.
choreograph AUTOSeveral things moving together: what leads, what follows, what overlaps, what stays still. Staggers, hero entrances, one view swapping for another.
gestures AUTODrag, swipe, sheets and drawers that follow the finger one for one, carry the speed of the release and can be caught mid-move.
animate-expo AUTOThe same, for React Native and Expo apps: gestures, sheets, haptics, screen changes.
prototype /SLASHBuilds several genuinely different versions of a piece of UI behind a switcher, so you flip through them live and pick. Three shades of one idea defeats the point, so it forces real differences.
pick-ui-library /SLASHPicks a library from Emil's trusted list (dropdowns, toasts, drawers, charts, drag and drop) instead of hand-rolling one or installing something abandoned. It checks what you already use first.
ask-sonner AUTOEverything about the Sonner toast library: setup, loading and promise toasts, styling, and toasts that do not appear or appear twice.

Check

review-animations /SLASHStrict review of the motion in a diff against ten non-negotiable standards. Flags by default.
break-ui AUTOFeeds a screen worst-case data (long names, empty lists, huge counts, emoji, non-Latin text) behind a "Demo data / Worst case" toggle, then reports what broke and how to fix it.
animation-performance AUTOFixes motion that drops frames: which properties are cheap to animate, when to use CSS or JS, and finding the real cause.
mobile-native AUTOThe small fixes that make a web app feel installed on a phone: sticky hover, tap flashes, the 100vh bug, inputs that zoom the page, the notch, and testing on real hardware.

Upkeep, on a codebase that already exists

improve-animations AUTO READ-ONLYAudits all the motion in a project and writes prioritised plans another agent can carry out.
find-animation-opportunities AUTO READ-ONLYFinds places that should animate and, as importantly, rejects the ones that should not. Proposes exact values; does not build them.
remove-animations AUTOTakes out motion the app does not need: on keyboard shortcuts, on things used constantly, decoration. It only subtracts.

Knowledge underneath

emil-design-eng AUTOHis core philosophy for polish: press and hover states, where a popover grows from, tooltip timing, the invisible details. The fallback when no narrower skill fits.
apple-design AUTOApple's approach to fluid, physical interfaces from their design talks, translated for the web.
animation-vocabulary AUTOTurns a vague description into the exact term ("the iOS rubber-band scroll" is rubber-banding) so you can prompt precisely.
write-swift AUTOModern Swift 6, concurrency and native iOS code. Nothing to do with the web.

Helpers

ask-emil /SLASHA router. Describe your situation and it recommends one skill and says why.
learn-taste /SLASHRun at the end of a working session. It collects every correction you made, including edits you made yourself, and turns each into a written rule with its reason so the next session does not repeat the mistake. It proposes first and writes only what you approve.

Three habits that get the most out of them

  1. Build, then break, then review. After animate or choreograph, run break-ui and /review-animations before calling it done.
  2. Use /prototype when you cannot settle it in words. Looking at four versions beats describing one.
  3. End long sessions with /learn-taste. Run it before you clear the conversation, so your corrections become rules in the project.

Applying them to all your sites, now and later

Skills load from the folder of whatever project Claude Code is opened in, so each repository needs its own copy, or you need a copy that follows you everywhere. Here is what is true today.

WhereStatusWhat to do
This repository (rhyshume.co.uk)Installed and pushedNothing. They load in any session on it.
Your other repositoriesNot installed. I can only reach this one from hereOpen a session on each repo, say "copy Emil's skills into this repo's .claude/skills from the rhyshume repo, then commit". The folder is plain files.
Your own computer, every projectNot set upRun npx skills@latest add emilkowalski/skills, the repository's own installer. Claude Code reads skills kept in ~/.claude/skills in every project, and the Mascot Designer and Google Ads installers use that same place.
Cloud sessions, every repoPossible, untestedA setup script on your cloud environment could download the skills into the container each time it starts. I have not tried it, and changing the environment needs your approval. Ask me if you want it.

Make new projects pick them up

For any new site, add this line to the project's CLAUDE.md, so Claude reaches for the skills without being told:

For UI, animation or interaction work, use the installed skills
(animate, choreograph, gestures, mobile-native, break-ui). Run
/review-animations before finishing motion changes.
One thing to watch on Tolra. Its CLAUDE.md says "do not go looking for problems; only do what is asked". Three of these skills (improve-animations, find-animation-opportunities, remove-animations) are exactly that kind of search. Run them only when you ask, and leave them out of the line above.

Updating later: run the same npx skills@latest add emilkowalski/skills on your computer, or ask Claude to re-copy the folder from the repository. Licence: MIT, kept alongside the skills in .claude/skills/_emilkowalski/.
